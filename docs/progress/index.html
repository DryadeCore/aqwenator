aqwenator

A handrolled inference server for the Qwen3.5 hybrid family (Gated DeltaNet plus gated attention), written in Rust with kernels compiled by cuda-oxide. Every comparison runs aqwenator and vLLM on the same machine: an NVIDIA B200 (development, shared with other users) or a DGX Spark (target hardware). Latency is reported at the tail (p99, p99.9).

Agentic workload: concurrent multi-turn agents

Each agent shares a 4,096-token system prompt, starts with a 1,024-token task, then loops: generate 256 tokens, receive a 512–4,096-token tool result after a 0.5–3 s tool delay, and continue until its context reaches 32k, then starts a new session. Both engines run Qwen3.5-9B under the same 32 GB memory budget (the size of an RTX 5090). Higher turns per minute at a bounded tail is the goal.

Where aqwenator's time goes

Share of GPU time per operation, each op timed in isolation. Prefill is the bottleneck at 1024-token prompts; the attention and DeltaNet chunk kernels still run on CUDA cores, and tensor-core versions are next.

Correctness against transformers

The reference is transformers in bf16. Teacher-forced: the reference's own tokens are fed through our decode path and every logits row is compared; a top-1 disagreement where the reference's top-2 margin is under 0.25 counts as a near-tie, anything else as a real miss. Session resume and shared-prefix fork compare a cached turn with a cold prefill of the same prompt. The suite also runs with odd step budgets and chunk sizes, which is how an upload/compute stream race was found and fixed.

How these numbers are made
  • vLLM: vllm serve plus vllm bench serve with the random dataset, --ignore-eos, max model length 16384, 256 max sequences, default settings otherwise. Its log notes that FlashInfer's precompiled cubins and DeepGEMM were unavailable for this model on B200.
  • aqwenator: aq-bench, an in-process closed loop with the same shapes and concurrency. It has no HTTP or tokenization yet, which slightly favors it; the HTTP server comes next so both can use the same client.
  • Workloads: 1024 prompt tokens with 256 output tokens, and 8192 prompt tokens with 512 output tokens. Prompts are random token ids.
  • Builds: m2 has the batched engine; m2g adds CUDA graphs; m3b adds the chunked DeltaNet prefill and tiled attention.
  • The B200 is shared with other users. Runs use a GPU that was idle at launch, but other users' jobs sometimes landed on the same GPU later. The DGX Spark runs are on a dedicated, otherwise idle machine.
  • Builds: m3c adds split-K decode attention and vectorized small kernels; spark1 is the first DGX Spark build (tensor-core attention and DeltaNet, session cache, upload race fixed).
